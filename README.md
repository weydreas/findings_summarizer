# Findings Summarizer — прямой комментарий + сравнение с extract

Локальная CLI-утилита для медицинских OCR/HTML-масок. Два пути от общего восстановленного текста:
1. **Основной direct:** исправленный текст → COMMENT_SYSTEM → комментарий в верхнеуровневом поле comment. Этот контракт предназначен для будущей интеграции с .NET-кабинетом.
2. **Сравнительный extract:** исправленный текст → EXTRACT_SYSTEM → структурированные факты → COMMENT_SYSTEM → второй комментарий с фактами в поле comparison.

Это черновики, а не медицинские заключения. Автоматической семантической оценки нет: ok=true означает успешную техническую обработку, не клиническую достоверность. Проверяет Аня.

## Инфраструктура

Используется работающая на сервере Qwen3-1.7B Q4_K_M через llama.cpp: http://llm:8080/v1/chat/completions во внутренней Docker-сети text-to-voice-tg-bot_default. Нет отдельной модели, фоновой службы, публикации порта и доступа к токенам Telegram-бота. Изменения не требуют перезапуска llm, bot или tts.

Обновление на VDS:

~~~bash
cd ~/apps/findings_summarizer && git pull --ff-only origin main && docker compose --profile medical build findings
~~~

Первая установка: клонируйте репозиторий и выполните ту же сборку. Проверка конфигурации: docker compose --profile medical config --quiet.

## Рекомендуемый запуск тестов: результат всегда в test_results

**Используйте run_test.py вместо вывода через > в корень проекта.** Скрипт работает на хосте VDS и запускает одноразовый контейнер:

~~~bash
cd ~/apps/findings_summarizer && python3 run_test.py examples/medical_summary_synthetic.json
~~~

Для собственного файла:

~~~bash
cd ~/apps/findings_summarizer && python3 run_test.py inputs/mask-01.json
~~~

Каждый запуск создаёт уникальную подпапку test_results/<UTC_timestamp>_<document_id>_<random>/ с файлами:
- input.json — оригинальный документ для сверки Аней;
- direct.json — основной комментарий, восстановленный текст;
- extract.json — сравнение: старый алгоритм, диагнозы, находки, измерения и второй комментарий либо код ошибки;
- result.json — полный объединённый ответ программы;
- run.json — технические метаданные и код завершения;
- stderr.log — диагностика контейнера, если присутствует.

Новые прогоны не перезаписывают старые. При технической ошибке вместо пустого файла записывается JSON с кодом ошибки. Права каталога 0700, файлов 0600. test_results/, inputs/, outputs/ исключены из Git. Репозиторий публичный: никогда не публикуйте реальные медицинские документы или результаты в GitHub. Доступ к хранению, экспорту и удалению данных должен быть ограничен организационными правилами.

Для сотен кейсов запускайте скрипт по очереди: Qwen общая с Telegram-ботом, сервер на CPU с -np 1, два метода увеличивают нагрузку.

## Формат запроса

~~~json
{
  "document_id": "test-renal-001",
  "format": "text",
  "content": "Основной диагноз: гипертензия. УЗИ почек: правая почка без изменений. В левой почке киста."
}
~~~

format: text, html или auto. content: до 16000 символов. document_id: технический идентификатор (не ФИО), до 100 символов.

## Формат ответа для будущего .NET-кабинета

~~~json
{
  "ok": true,
  "schema_version": "medical-summary-v2",
  "document_id": "test-renal-001",
  "primary_method": "direct",
  "restored_text": "Восстановленный текст исследования",
  "comment": "Основной медицинский комментарий.",
  "comparison": {
    "ok": true,
    "method": "extract",
    "comment": "Сравнительный комментарий.",
    "diagnoses": [],
    "findings": [],
    "measurements": [],
    "treatments_and_followup": [],
    "uncertainties": [],
    "review_flags": []
  },
  "review_required": true,
  "review_flags": ["Черновик ИИ: сверить с оригинальным документом перед публикацией."]
}
~~~

При ошибке сравнения основной comment сохраняется, а comparison получает ok=false и error с техническим кодом. При ошибке основного метода возвращается верхнеуровневый ok=false. Отдельного API и .NET-интеграции пока нет; здесь фиксируется формат выходных данных, не механизм отправки.

## Длинные документы

Когда восстановленный текст помещается в консервативный лимит прямой генерации, он идёт в Qwen целиком. Для длинных документов, которые не помещаются в общий контекст 4096 токенов, основная ветка формирует промежуточные короткие комментарии по блокам и объединяет их последующим прямым вызовом. Текст не обрезается молча, но возможны смысловые потери: требуется проверка специалистом.

Сравнительный метод использует прежнюю JSON-схему и алгоритм. Три утверждённых системных промпта не менялись. Оба метода получают один и тот же восстановленный текст.

cd ~/apps/findings_summarizer && docker compose --profile medical run --rm --no-deps -T findings python -m unittest discover -s tests -v

## Набор из двух эталонных входов для сравнения моделей

В репозитории хранятся два **фиксированных** тестовых документа:

| Файл | Тип | Размер текста |
| --- | --- | --- |
| examples/medical_summary_synthetic.json | Короткое синтетическое УЗИ сосудов почек | ~570 символов |
| examples/discharge_epicrisis_deidentified.json | Длинный выписной эпикриз с лабораторными таблицами, назначениями и OCR-шумом | ~33 500 символов |

Для второго теста удалены личные данные пациента, врачей, адреса, номера карт и учреждения. Дата рождения удалена, возраст сохранён, даты посещений и анализов сдвинуты на условные. Медицинские показатели, диагнозы, описания исследований и структура с OCR-артефактами сохранены как исходный материал для эксперимента. **Текст основан на реальном документе и не должен считаться доказанно необратимо анонимным**: сочетание медицинских фактов потенциально позволяет косвенную идентификацию. Не добавляйте в публичный репозиторий новые пациентские документы без отдельной проверки разрешения на публикацию и риска повторной идентификации.

На сервере выполните после слияния PR:

~~~bash
cd ~/apps/findings_summarizer && git pull --ff-only origin main && docker compose --profile medical build findings
~~~

Единый запуск **обоих** случаев последовательно, при этом оба метода сохраняются автоматически:

~~~bash
cd ~/apps/findings_summarizer && python3 run_suite.py --model-label qwen3-1.7b-q4km
~~~

В будущем при переключении модели используйте другой параметр --model-label (например, имя и квантование новой модели), чтобы Аня могла группировать результаты по нейросетям. Фактический выбор модели определяется конфигурацией LLM-сервера, **параметр --model-label только подписывает результат**.

Каждый кейс создаёт новую приватную подпапку test_results с input.json, direct.json, extract.json, result.json и run.json. Модели **не сравниваются автоматически по клинической точности**: это задача ручной экспертизы Ани.

Для больших документов действует лимит 65 536 символов. Общая Qwen пока использует серверный контекст 4096 токенов, поэтому длинный эпикриз будет обработан многими последовательными запросами по блокам как в direct, так и в extract; возможно снижение качества связности и большая нагрузка на CPU. Никаких изменений контекста сервера этот тестовый набор не делает.


## Восстановление сложного OCR: адаптивные повторы и прозрачность

Если Qwen возвращает при восстановлении фрагмента подозрительно короткий или длинный текст (RESTORATION_LENGTH_MISMATCH) либо обрывает генерацию (RESTORATION_TRUNCATED), Summarizer сначала повторяет восстановление на меньших фрагментах. Если фрагмент уже слишком мал для безопасного деления, в восстановленный текст подставляется **исходный фрагмент без изменений** (не выдумывается утраченная информация).

Это поведение делает тестирование длинных эпикризов устойчивее, но не подтверждает медицинскую корректность комментария. В полном result.json и в direct.json сохраняется секция restoration с числом повторных делений, числом и общим объёмом фрагментов без восстановления и кодами причин. При таких фрагментах review_flags содержит явное предупреждение для Ани. Ошибки связи с LLM не скрываются и остаются фатальными.

**Осторожно:** исходные OCR-артефакты могут остаться в отдельных участках документа. Результаты должны сравниваться с исходным файлом, особенно назначения и числовые показатели. Если ok=true, это лишь техническое завершение, не клиническое одобрение.


## Длинные документы: контроль завершения комментария и прогресс

Если Qwen обрывает прямой комментарий по лимиту токенов (finish_reason=length; на общем сервере max_tokens=480), программа не принимает обрезанный ответ. Она повторяет формирование комментария по более коротким фрагментам (минимум 200 символов) и затем делает итоговый проход. Если даже маленький фрагмент невозможно закончить, возвращается техническая ошибка DIRECT_COMMENT_TRUNCATED_MIN_CHUNK: такой текст **не публикуется**. Для длинных документов допускается до 8 проходов иерархического сокращения. Медицинская полнота итогового текста всё равно требует ручной проверки Аней.

При запуске через run_test.py автоматически включается служебный прогресс без медицинского текста: в индивидуальной папке теста сразу создаётся stderr.log, который обновляется во время работы. На экран в начале выводятся пути Processing: и Progress log:. Проверить прогресс можно командой вида:

~~~bash
tail -n 20 ~/apps/findings_summarizer/test_results/ПАПКА_ТЕСТА/stderr.log
~~~

Там появляются только стадии и номера частей: PROGRESS restore, direct_pass, direct_piece, direct_split_retry, direct_complete, extract, extract_comment_batch, comparison_complete. Отсутствие новой строки некоторое время само по себе не означает зависание: Qwen на CPU может генерировать ответ долго.

Финальные JSON по-прежнему записываются только по завершении. Важное ограничение: **промежуточные медицинские результаты пока не сохраняются для возобновления**. Повтор после ошибки заново обрабатывает исходный текст; не запускайте одновременно два экземпляра на общей LLM. Архив прежних неудачных прогонов сохраняется.


## Режим нативного контекста 32K: опциональная оптимизация

Общий llama.cpp из text-to-voice-tg-bot должен **сначала** быть обновлён до -c 32768 и проверен. Без этого настройка ниже может приводить к переполнению контекста на длинном документе. По умолчанию Findings остаётся в проверенном режиме legacy (старое окно 4096).

Запустить один тест в новом режиме можно, не меняя .env и не затрагивая Telegram-бота:

~~~bash
cd ~/apps/findings_summarizer
FINDINGS_CONTEXT_PROFILE=32k python3 run_test.py examples/discharge_epicrisis_deidentified.json
~~~

В фоне:

~~~bash
cd ~/apps/findings_summarizer && FINDINGS_CONTEXT_PROFILE=32k nohup python3 -u run_test.py examples/discharge_epicrisis_deidentified.json > test_results/epicrisis-32k.log 2>&1 < /dev/null &
~~~

Параметр передаётся в однократный контейнер через compose.yaml. При 32k меняются **только** ограничители размеров запросов этого проекта:
- исходные OCR-блоки: 750 → 1500 символов;
- начальные прямые фрагменты: 1800 → 16000 символов;
- группы фактов для сравнительного комментария: 2400 → 8000 символов;
- лимит ответа модели на запрос: 480 → 2048 токенов.

Системные медицинские промпты, общий сервер Qwen, безопасность сети, модель и сравнение двух путей остаются прежними. Даже 16000 символов — не гарантия полного охвата всех сведений; это консервативный запас для русскоязычного текста при 32K токенов. Реальный выигрыш по времени и полноту комментария определяют только замеры. Превышение размера токенов конкретного запроса может по-прежнему вызвать ошибку; автоматический токенизатор или универсальное дробление по серверному числу токенов пока не добавлены.

Контекстный профиль сохраняется в test_results/.../run.json. Следите за стадиями в test_results/.../stderr.log, обозначенными в основном логе. Вернуться к прежнему режиму можно без пересборки: запускать run_test.py **без** FINDINGS_CONTEXT_PROFILE=32k. Ошибка в имени профиля приводит к INVALID_CONTEXT_PROFILE, а не к молчаливому выбору режима. Тесты 32K не имеют механизма возобновления после сбоя: повтор заново выполняет восстановление OCR.


## Временные отметки и длительность обработки

Каждая строка PROGRESS в приватном test_results/.../stderr.log теперь содержит UTC-время (ISO 8601), название этапа, завершённый блок, elapsed_s (секунды с запуска CLI внутри контейнера) и delta_s (секунды с предыдущей отметки). Эти числа считаются по монотонным часам и не зависят от корректировки системного времени.

Пример формата (условные значения, без медицинских данных):

~~~text
2026-11-12T09:00:00.123Z PROGRESS restore 1/23 elapsed_s=12.003 delta_s=11.998
2026-11-12T09:00:19.777Z PROGRESS restore 2/23 elapsed_s=31.657 delta_s=19.654
2026-11-12T09:03:00.456Z PROGRESS direct_pass 1/8 elapsed_s=192.336 delta_s=0.001
~~~

Появляются и контрольные отметки start, completed, failed или comparison_failed. Они отражают только технический ход, не медицинскую корректность. Если обработка оборвалась, последняя отметка помогает найти этап, где возникла проблема. Блоки на CPU могут занимать много времени.

Сам хостовый run_test.py теперь печатает Started UTC, Finished UTC и Elapsed seconds в основном журнале запуска (например, test_results/epicrisis-32k.log). В test_results/.../run.json сохранены started_at_utc, finished_at_utc, duration_seconds и exit_code, включая ошибочные прогоны, если скрипт дошёл до архивации. Продолжительность измеряется монотонными часами хоста, поэтому является надёжным benchmark-показателем. Эта функция не меняет модель, промпты или число LLM-запросов.

**Важно:** изменения начинают действовать только для новых запусков после обновления и сборки контейнера. В старых логах нельзя восстановить время каждого шага задним числом; приблизительную общую длительность прежнего теста можно оценить по UTC времени в названии папки и времени изменения run.json, если этот файл существует.


## Экспериментальный evidence_v1: медицинские факты перед генерацией

По умолчанию все прежние алгоритмы работают без изменений. Новый исследовательский пайплайн включается параметром FINDINGS_PIPELINE_MODE=evidence_v1 одновременно с FINDINGS_CONTEXT_PROFILE=32k, если общий llama.cpp сервер уже настроен на 32768 токенов. Режим legacy остаётся умолчанием. Telegram-бот-наставник, веса модели и промпты старого режима не меняются.

Новый режим сделан по мотивам научных направлений: атомарные факты, выделение значимого до написания резюме, подтверждающие цитаты, постгенерационные проверки и целевой повтор только непокрытых важных фактов. Это инженерная реализация подходов, **не копия и не доказанная клиническая эффективность** конкретной научной системы.

Конвейер evidence_v1:

1. **Source + sectionize** — разделение исходного OCR по клиническим заголовкам, затем по ограниченным блокам. Исходный текст НЕ перезаписывается моделью; каждый блок связан с символьным диапазоном оригинала.
2. **Source anchors** — консервативно отмечаем явные строки основного диагноза/осложнений и однозначные однострочные отклонения результатов от диапазона. Неоднозначные таблицы не интерпретируем автоматически.
3. **Evidence extraction** — Qwen возвращает атомарные факты с дословными цитатами. К фактам принимаются только цитаты, проверенные по исходному тексту, с указанием диапазона; неверифицированные цитаты считаются ошибками контроля.
4. **Evidence synthesis** — Qwen формирует черновик по ограниченным пачкам фактов с ссылками [F0001]. Готовые части объединяются без дополнительного сжимающего общего прохода.
5. **Quality gate** — проверяет неизвестные ссылки, отсутствие обязательных фактов, строки без ссылок и подозрительные заявления о норме рядом с доказанными отклонениями. Пропущенные обязательные факты запускают только *локальную* попытку восстановления.
6. **Semantic audit** — только после механических проверок та же Qwen отдельно оценивает черновые утверждения относительно процитированных фрагментов и отмечает неподтверждённые утверждения, ошибки измерений, нормальности, дат и лечения. Замечания ведут к ok=false, но отсутствие замечаний не доказывает корректность. При невосстановимой проблеме ok=false и ненулевой код выхода; результаты всё равно сохраняются.

Новый режим **не** доказывает исчерпывающую полноту извлечения, клиническую интерпретацию, семантическую истинность каждого предложения или правильность связей в повреждённых OCR-таблицах. Наличие ссылки [F0001] не гарантирует, что всё предложение действительно следует из цитаты. automated_gate_passed=true — только прохождение перечисленных механических тестов, не разрешение на публикацию пациенту. Всегда review_required=true.

На сервере после обновления и сборки:

~~~bash
cd ~/apps/findings_summarizer && git pull --ff-only origin main && docker compose --profile medical build findings
FINDINGS_CONTEXT_PROFILE=32k FINDINGS_PIPELINE_MODE=evidence_v1 python3 -u run_test.py examples/discharge_epicrisis_deidentified.json
~~~

В фоне, без параллельных запросов к общей Qwen:

~~~bash
cd ~/apps/findings_summarizer && FINDINGS_CONTEXT_PROFILE=32k FINDINGS_PIPELINE_MODE=evidence_v1 nohup python3 -u run_test.py examples/discharge_epicrisis_deidentified.json > test_results/epicrisis-evidence-v1.log 2>&1 < /dev/null &
~~~

Путь к отдельному stderr.log будет в начале общего журнала. В нём только стадии, счётчики, UTC-отметки и длительности (никаких цитат из эпикриза). По завершении run_test.py приватно архивирует старые input.json, result.json, direct.json, extract.json, run.json, а также:

- sections.json: номера и смещения блоков в исходном OCR;
- facts.json: реестр фактов с клиническим текстом, точными источниками и обязательностью;
- drafts.json: промежуточные черновики со ссылками на факты;
- quality.json: результаты автоматического контроля и список пропусков.

**Не выкладывайте эти четыре файла в GitHub**: они содержат медицинские сведения и хранятся исключительно в игнорируемом test_results/ на хосте с разрешением 0600. Вывод результатных JSON не поступает в бот и не доступен через сеть.

Для сравнения со старой веткой запустите прежний тест отдельно, **без** FINDINGS_PIPELINE_MODE (или с legacy). Но сравнение времени включает и различную обработку OCR: evidence_v1 сохраняет исходный OCR вместо множества вызовов генеративного восстановления. Для научного сравнения качества нужен независимый размеченный набор фактов и оценка специалистом, а не одно ok=true.


## Новый экспериментальный режим semantic_v2 (семантическая самопроверка)

Режим добавлен отдельно от legacy/direct и evidence_v1; существующие результаты и алгоритмы не меняются. Основан на разделении ролей при чтении, независимой *сессии* проверки и повторном анализе исходного документа вместо сопоставления медицинских слов и цитат через регулярные выражения.

Включение: FINDINGS_PIPELINE_MODE=semantic_v2 и FINDINGS_CONTEXT_PROFILE=32k (общий сервер llama.cpp должен быть поднят с поддержкой 32768 токенов).

Этапы:

1. Исходный OCR сохраняется без преобразования нейросетью. Python делит его на ограниченные фрагменты **только по размеру**, без клинических регулярных выражений и списка заголовков.
2. Qwen в роли извлекателя получает один фрагмент; возвращает короткие атомарные клинические утверждения, включая отрицания и временные ограничения.
3. В НОВОМ запросе, с новой системной ролью и без истории извлечения, Qwen получает исходный фрагмент и предложенные утверждения. Проверяет поддержку, противоречия, неопределённость и пропуски. Все отклонённые и спорные факты сохраняются с объяснением, но не используются для генерации.
4. Python выполняет **только** сопоставление числовых литералов, дат и явных единиц измерения с тем же фрагментом; при несовпадении блокирует использование факта. Это не валидатор медицинского смысла или референсов.
5. Qwen как редактор выбирает ограниченный набор клинически значимых проверенных фактов, затем делает ОДИН связный текст без ручных клинических фильтров и требования форматировать ссылочные ID.
6. Другой НОВЫЙ запрос Qwen в роли итогового рецензента получает целиком оригинальный OCR и окончательный текст, но НЕ получает историю извлечения, промежуточные факты, выбор редактора или прошлые выводы. Отмечает противоречия, отрицания, искажения дат/значений и существенные пропуски. Итоговая проверка выполняется даже без формальных ссылок в тексте.

Никаких регулярных выражений по клиническим терминам, названиям диагнозов, словам "норма"/"нет" или ссылкам вида [F0001] в новом режиме нет. Механическая проверка существования идентификаторов и корректности JSON сохраняется исключительно для целостности протокола; клиническая трактовка определяется отдельными запросами Qwen.

**Ограничения.** Проверяет работу ТА ЖЕ Qwen3-1.7B, но в новой роли/контексте: нет гарантий независимости ошибок, исчерпывающего извлечения, верного анализа исходных повреждённых OCR-таблиц или клинической пригодности. Числовая проверка лишь устанавливает встречаемость значения/единицы/даты в доступном фрагменте, не проверяет принадлежность чисел одному исследованию и не заменяет семантическую проверку. Даже если automated_gate_passed=true, review_required=true и нужна независимая клиническая проверка перед публикацией.

### Запуск

Сначала убедиться, что уже завершились другие запуски findings и что общий сервер Qwen не занят, затем:

~~~bash
cd ~/apps/findings_summarizer
git pull --ff-only origin main
docker compose --profile medical build findings
FINDINGS_CONTEXT_PROFILE=32k FINDINGS_PIPELINE_MODE=semantic_v2 python3 -u run_test.py examples/discharge_epicrisis_deidentified.json
~~~

Для отдельного фонового прогона:

~~~bash
cd ~/apps/findings_summarizer
FINDINGS_CONTEXT_PROFILE=32k FINDINGS_PIPELINE_MODE=semantic_v2 nohup python3 -u run_test.py examples/discharge_epicrisis_deidentified.json > "test_results/epicrisis-semantic-v2-$(date -u +%Y%m%dT%H%M%SZ).log" 2>&1 < /dev/null &
~~~

Точное расположение каталога результата напечатает run_test.py при запуске. В нём сохраняются приватно (0600): input.json, result.json, direct.json, extract.json, run.json, stderr.log, а также новые blocks.json, facts.json, reviews.json, selection.json и quality.json. Они содержат клинический текст и **никогда не должны помещаться в GitHub**. Этапы и их время пишутся в stderr.log без пациентского содержимого. Старый режим не запускается параллельно — это отдельный прогон.

Пока речь об эксперименте, а не валидированной медицинской системе. Оценку улучшений нужно проводить на том же обезличенном документе и заранее составленном перечне ключевых клинических фактов, затем на независимых историях с проверкой специалистом.
