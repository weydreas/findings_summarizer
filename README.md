# Findings Summarizer — прямой комментарий + сравнение с extract

Локальная CLI-утилита для медицинских OCR/HTML-масок. Два пути от общего восстановленного текста:
1. **Основной direct:** исправленный текст → COMMENT_SYSTEM → комментарий в верхнеуровневом поле comment. Этот контракт предназначен для будущей интеграции с .NET-кабинетом.
2. **Сравнительный extract:** исправленный текст → EXTRACT_SYSTEM → структурированные факты → COMMENT_SYSTEM → второй комментарий с фактами в поле comparison.

Это черновики, а не медицинские заключения. Автоматической семантической оценки нет: ok=true означает успешную техническую обработку, не клиническую достоверность. Проверяет Аня.

## Инфраструктура

Используется работающая на сервере Qwen3-1.7B Q4_K_M через llama.cpp: http://llm:8080/v1/chat/completions во внутренней Docker-сети text-to-voice-tg-bot_default. Нет отдельной модели, фоновой службы, публикации порта и доступа к токенам Telegram-бота. Изменения не требуют перезапуска llm, bot или tts.

Обновление на VDS:

~~~bash
cd ~/apps/findings_summarizer && git pull --ff-only origin main && docker compose --profile medical build findings
~~~

Первая установка: клонируйте репозиторий и выполните ту же сборку. Проверка конфигурации: docker compose --profile medical config --quiet.

## Рекомендуемый запуск тестов: результат всегда в test_results

**Используйте run_test.py вместо вывода через > в корень проекта.** Скрипт работает на хосте VDS и запускает одноразовый контейнер:

~~~bash
cd ~/apps/findings_summarizer && python3 run_test.py examples/medical_summary_synthetic.json
~~~

Для собственного файла:

~~~bash
cd ~/apps/findings_summarizer && python3 run_test.py inputs/mask-01.json
~~~

Каждый запуск создаёт уникальную подпапку test_results/<UTC_timestamp>_<document_id>_<random>/ с файлами:
- input.json — оригинальный документ для сверки Аней;
- direct.json — основной комментарий, восстановленный текст;
- extract.json — сравнение: старый алгоритм, диагнозы, находки, измерения и второй комментарий либо код ошибки;
- result.json — полный объединённый ответ программы;
- run.json — технические метаданные и код завершения;
- stderr.log — диагностика контейнера, если присутствует.

Новые прогоны не перезаписывают старые. При технической ошибке вместо пустого файла записывается JSON с кодом ошибки. Права каталога 0700, файлов 0600. test_results/, inputs/, outputs/ исключены из Git. Репозиторий публичный: никогда не публикуйте реальные медицинские документы или результаты в GitHub. Доступ к хранению, экспорту и удалению данных должен быть ограничен организационными правилами.

Для сотен кейсов запускайте скрипт по очереди: Qwen общая с Telegram-ботом, сервер на CPU с -np 1, два метода увеличивают нагрузку.

## Формат запроса

~~~json
{
  "document_id": "test-renal-001",
  "format": "text",
  "content": "Основной диагноз: гипертензия. УЗИ почек: правая почка без изменений. В левой почке киста."
}
~~~

format: text, html или auto. content: до 16000 символов. document_id: технический идентификатор (не ФИО), до 100 символов.

## Формат ответа для будущего .NET-кабинета

~~~json
{
  "ok": true,
  "schema_version": "medical-summary-v2",
  "document_id": "test-renal-001",
  "primary_method": "direct",
  "restored_text": "Восстановленный текст исследования",
  "comment": "Основной медицинский комментарий.",
  "comparison": {
    "ok": true,
    "method": "extract",
    "comment": "Сравнительный комментарий.",
    "diagnoses": [],
    "findings": [],
    "measurements": [],
    "treatments_and_followup": [],
    "uncertainties": [],
    "review_flags": []
  },
  "review_required": true,
  "review_flags": ["Черновик ИИ: сверить с оригинальным документом перед публикацией."]
}
~~~

При ошибке сравнения основной comment сохраняется, а comparison получает ok=false и error с техническим кодом. При ошибке основного метода возвращается верхнеуровневый ok=false. Отдельного API и .NET-интеграции пока нет; здесь фиксируется формат выходных данных, не механизм отправки.

## Длинные документы

Когда восстановленный текст помещается в консервативный лимит прямой генерации, он идёт в Qwen целиком. Для длинных документов, которые не помещаются в общий контекст 4096 токенов, основная ветка формирует промежуточные короткие комментарии по блокам и объединяет их последующим прямым вызовом. Текст не обрезается молча, но возможны смысловые потери: требуется проверка специалистом.

Сравнительный метод использует прежнюю JSON-схему и алгоритм. Три утверждённых системных промпта не менялись. Оба метода получают один и тот же восстановленный текст.

cd ~/apps/findings_summarizer && docker compose --profile medical run --rm --no-deps -T findings python -m unittest discover -s tests -v
~~~

Автоматические офлайн-тесты проверяют работу веток и сохранение результатов, но НЕ оценивают клиническую корректность. Содержательную оценку по сотням документов делает Аня. Реальные пациентские данные должны обрабатываться с утверждёнными правилами защиты персональной медицинской информации.
