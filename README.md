# Findings Summarizer — медицинские OCR/HTML-маски через локальную Qwen

Экспериментальная CLI-утилита: восстановление очевидных OCR-артефактов, выделение клинически значимых находок (включая **нормальные** результаты по отдельным органам), диагнозов и параметров, затем краткий комментарий для проверки человеком. На вход — один UTF-8 JSON; на выход — один JSON. **Не является медицинским заключением без проверки.**

## Принцип: используем уже работающую Qwen

На VDS `srv-prod` уже запущен `Qwen3-1.7B Q4_K_M` в `llama.cpp`, адрес внутри Docker — `http://llm:8080/v1/chat/completions`. **Новый сервер Qwen, модель, RAG и Telegram-бот не запускаются**. Этот репозиторий содержит только одноразовый клиент, Dockerfile, синтетический пример и тесты.

`Docker Compose` подключает клиент к существующей Docker-сети `text-to-voice-tg-bot_default`. Адрес сети выведен из имени Compose-проекта Telegram-бота; **до запуска проверьте реальное имя**. Сетевой порт на хост не публикуется. Клиент не читает `.env` Telegram-бота и не монтирует его данные.

## SSH — подготовка на VDS

Сначала проверить имя Docker-сети, без изменений работающих процессов:

~~~bash
docker network ls --format '{{.Name}}' | grep text-to-voice-tg-bot
~~~

В отдельной директории (не внутри проекта Telegram):

~~~bash
cd ~/apps && git clone https://github.com/weydreas/findings_summarizer.git && cd findings_summarizer && git switch feat/ssh-json-qwen-summary && docker compose --profile medical config --quiet && docker compose --profile medical build findings
~~~

Если после merge код станет доступен в main, переключение на feature-ветку не нужно. Для другого имени сети задаётся переменная `LLM_DOCKER_NETWORK` при запуске docker compose; **не открывайте порт Qwen наружу**.

## Первый прогон (синтетический документ)

Самый безопасный тест — синтетический файл из репозитория. Не содержит данных пациентов.

~~~bash
cd ~/apps/findings_summarizer && docker compose --profile medical run --rm --no-deps -T findings < examples/medical_summary_synthetic.json > demo-result.json && python3 -m json.tool demo-result.json
~~~

Один запуск запускает отдельный клиентский контейнер, использует существующую LLM, сохраняет ответ на хосте и завершается. На CPU это может быть медленно; у существующего `llama.cpp` `-np 1`, поэтому одновременно работающий Telegram-бот может отвечать с задержкой. **Не нужно пересобирать или перезапускать llm, bot или tts**.

## Тестирование

~~~bash
cd ~/apps/findings_summarizer && docker compose --profile medical run --rm --no-deps -T findings python -m unittest discover -s tests
~~~

Тесты используют фиктивный документ и mock HTTP, поэтому не вызывают Qwen. Перед первым live-прогоном обязательно выполнить также синтетический end-to-end тест выше.

## JSON-запрос

~~~json
{
  "document_id": "test-renal-001",
  "format": "text",
  "content": "Основной диагноз: гипертензия. УЗИ почек: правая почка без изменений. В левой почке киста."
}
~~~

- `format`: `text`, `html` или `auto` (по умолчанию).
- `content`: медицинский текст или HTML в JSON-экранированной строке, до 16 000 символов.
- `document_id`: безопасный технический идентификатор (не ФИО), до 100 символов.

Для двух пользовательских тестовых масок подготовить собственные `mask-01.json`, `mask-02.json` в приватной рабочей директории VDS и подать через редирект, как показано выше. **Не коммитить HTML, заключения, медицинские документы или результаты в GitHub**. Репозиторий публичный.

## Выходной JSON

Выход содержит: `ok`, `schema_version`, `document_id`, `restored_text`, `comment`, `diagnoses`, `findings` (объект с `site`, `status`, `description`, `evidence`), `measurements`, `treatments_and_followup`, `uncertainties`, `review_required`, `review_flags`.

Для `findings.status` значения: `normal`, `abnormal`, `uncertain`. Раздельно сохраняются выявленные отклонения и явно нормальные показатели по другим органам. Неясные дозировки и единицы **не угадывать**; результат всегда требует сверки с оригиналом (`review_required=true`).

Внутренний процесс: (1) консервативное исправление OCR небольшими блоками, (2) извлечение фактов с JSON-schema-ограничением llama.cpp, (3) краткий комментарий по извлечённым фактам. При обрыве ответа, неверном JSON и подозрительно больших пропусках CLI пытается безопасно разделить блок или возвращает ошибку, а не публикует неполный комментарий. Возможны ошибки и пропуски: это пока экспериментальный прототип без клинической валидации.

## Архитектура корпоративного доступа — следующий этап

Для Biodata позднее предусмотрен отдельный API Gateway, доступный только через подтверждённый корпоративный VPN, с аутентификацией, ограничением доступа и журналированием **без медицинского содержимого**. Он сможет обращаться к тому же внутреннему Qwen. **Этот PR не создаёт gateway, VPN-доступ или публичный listener**. Текущий SSH-режим предназначен для проверки синтетических данных; работа с настоящими медицинскими записями требует отдельного согласования защиты данных и среды исполнения.

## Известные ограничения

- Наш `llama.cpp`: контекст 4096 токенов, лимит ответа сервера 512 токенов; CLI разделяет большие входы.
- Оба вида генерации (Telegram-ответы и summary) используют одни CPU и очередь Qwen.
- Качество исправления OCR и полнота извлечения пока не подтверждены живым запуском на VDS.
- Никаких весов, образцов голоса, токенов или медицинских документов в репозитории нет.
